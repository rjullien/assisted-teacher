# Multi-turn Hermes tool loop and two Desk sub-modes

`callHermesStream` stops being a single POST per user message and becomes an OpenAI-style function-calling loop: it declares `read_file`, `write_file` and `patch_file`, accumulates streamed `tool_calls` deltas, runs the tools locally against `WORKSPACE_DIR` through the pre-existing `safePath`, feeds `role:"tool"` results back and re-posts until a turn comes back without tool calls or the 8-loop cap is hit. Mode Desk is then split into two sub-modes — `insert` (today's copy/insert behaviour, no tools declared at all) and `direct` (Lya edits the working file, whose path is shown at the top of the panel) — behind a single gate, `fileToolsEnabled(mode, deskMode)`, which also now gates the v1.9.0 `hermes.tool.progress` write interception. `pi.go`, `LyaChat.tsx` and `version.json` are untouched, `buildDeskPrompt` and `MAX_INLINED_FILE_CHARS` are intact, and the loop is proven against a scripted fake gateway with mutation-verified tests.

Watch for: the Desk prompt still tells Lya *"tu n'as pas accès à mon dossier de travail, ne cherche pas à l'ouvrir"* in the `direct` sub-mode, which is the exact behaviour the tools are supposed to enable (**confirmed**, blocking); tool failures are emitted as `status:"error"` events that the frontend renders identically to successes, so a refused write reads as *"✏️ Écriture de …"* in the thread (**confirmed**); an absent or unknown `deskMode` resolves to `direct`, so any client that does not send the field gets the write tools armed (**confirmed**, deliberate but worth a second look); and the write tools are workspace-wide, not scoped to the working file the panel names (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The degradation story is the strong part of the change: `[DONE]` now ends a *turn* rather than the job, the `done` event is only appended when a turn came back with no tool calls, and a gateway that ignores `tools` produces exactly one request and exactly the old event sequence. One `hermes: tool_calls supported=true|false (mode=… deskMode=… loops=… toolCalls=…)` line per job carries the sub-mode too, so production logs can settle the one thing this sandbox cannot — whether the gateway forwards `tools` upstream. Nothing in the code, comments or commit messages claims it was verified.

The prompt layer contradicts the tool layer. `buildDeskPrompt` is unchanged (as required) and still inlines the file with a context line stating Lya has no access to the working directory and must not try to open it — and it runs in both sub-modes. In `direct` the request declares three file tools while the user turn tells the model those tools do not exist, and nothing in the system prompt mentions them. No test breaks, but this is the most likely reason the feature would look dead in production, and the `supported=false` diagnostic would then be blamed on the gateway.

Gating is genuinely centralised: one function decides both declaration and execution, unsolicited `tool_calls` outside that gate are refused and logged instead of executed, and the same gate was extended over the v1.9.0 progress-frame interception. Two consequences: the frontend defaults to `insert` while the backend maps *absent or unknown* `deskMode` to `direct`, so the safe default and the permissive default sit on opposite sides of the wire; and because the v1.9.0 interception is now sub-mode gated, teachers on v1.9.1 who relied on Lya writing files lose that path silently until they flip the new toggle.

The blast radius of the direct sub-mode is wider than the UI suggests. The banner names one working file, but `write_file` and `patch_file` accept any relative path in the workspace; `read_file` has no extension allowlist at all, so anything under `WORKSPACE_DIR` can be shipped to the gateway even though writes are restricted to `.md/.json/.txt`; and written content is unbounded while reads are capped at 20000 runes.

Tool results accumulate in `messages` for up to eight round-trips with no cumulative budget, so a couple of large `read_file` results can push the conversation past the upstream context window; that failure arrives as a gateway 4xx and reaches the teacher as the generic *"Échec IA. Réessaie."*.

Backend tests drive real WebSocket jobs against a scripted gateway and assert on the declared `tools` array, the `role:"tool"` messages fed back, files actually created and patched in `t.TempDir()`, and exact request counts for the loop cap and the degradation path; every guard was mutation-verified, including one surviving `safePath` mutant that was closed by re-testing traversal with an allowed extension. The gaps are in reassembly and dispatch: unknown tool names, malformed argument JSON, two tool calls in one turn, and the synthesised `call_<i>` id are all unexercised.

## The Desk prompt still tells Lya she has no file access

`buildDeskPrompt` is called whenever a file is open with content, regardless of sub-mode (`Chat.tsx`):

```
[Contexte: je travaille sur le fichier "B1/unite1.md". Son contenu est reproduit
ci-dessous : tu n'as pas accès à mon dossier de travail, ne cherche pas à l'ouvrir.]
```

In `direct` that user turn travels in the same request as `tools: [read_file, write_file, patch_file]` and `tool_choice: "auto"`, and `buildSystemPrompt` never mentions tools either. The instruction is explicit enough that a compliant model answers with text instead of calling `patch_file`, which is precisely the *"si je dis update ce fichier"* case the change is for (**confirmed** — string at `Chat.tsx:183`, call site at `Chat.tsx:620-623`, unconditional on `deskSubMode`).

The constraint to keep `buildDeskPrompt` and its cap does not require keeping the wording in both sub-modes: the fallback stays intact if the context line is sub-mode aware — inlining the file as today but stating that the working file can also be read and edited with the tools in `direct`. Without that, `supported=false` will be read as "the gateway drops `tools`" when the real cause is on this side.

## Writes on the last loop iteration

On iteration 8 the loop still executes the tools it was handed, then exits and emits *"Boucle d'outils interrompue après 8 échanges. Relance la demande en la découpant en étapes plus petites."*. A write can therefore land as the very last action with no confirming turn, leaving the teacher a warning that reads like an abort and a modified file with no statement of what changed (**confirmed**). The `file_changed` event still fires, so the editor reloads; the message is what misleads.

## One gate, and the meaning of an absent `deskMode`

`fileToolsEnabled(mode, deskMode)` is the only place mode is consulted, and `streamTurn` now routes the v1.9.0 `handleToolFileWrite` interception through it as well, so the copy/insert sub-mode cannot be mutated by a write-flavoured progress frame either. `normalizeDeskMode` maps `insert` (case- and space-insensitive) to `insert` and *everything else* — absent, empty, `"direct"`, `"garbage"` — to `direct`, with a comment arguing that a deployed frontend unaware of the field must not silently stop writing files.

That argument holds for v1.9.x parity, but it puts the fail-open direction on the default path for a capability much stronger than the progress-frame interception: any client that omits the field, or sends a typo, gets `read_file`/`write_file`/`patch_file` armed without ever having opted in (**confirmed** — `TestNormalizeDeskMode` asserts `"garbage" → direct` as intended). A middle ground: keep the v1.9.0 interception on an absent field (true parity) and require an explicit `direct` for the new tools.

The mirror image is a migration gap: the frontend defaults to `insert`, and `insert` now also disables the v1.9.0 write path, so a teacher who was getting file writes on v1.9.1 stops getting them after this ships until they discover the toggle (**confirmed**). Nothing in the UI signals that the previous behaviour moved behind a switch.

## The direct sub-mode is workspace-wide, not working-file-scoped

The panel says *"✍️ Fichier de travail : B1/unite1.md"* and the comment in `Chat.tsx` reasons that an edit landing in an unexpected course file is not something a teacher can undo. Nothing enforces that scope: `currentFile` travels as observability only, and the executors take whatever relative path the model produced. `safePath` keeps it inside `WORKSPACE_DIR`, but inside it the model can rewrite any `.md/.json/.txt` (**confirmed**). Comparing the model's `path` against the announced working file — refusing, or at least flagging, a write elsewhere — would make the UI's promise real.

Two asymmetries in the same area. `read_file` runs no extension check, so any file under `WORKSPACE_DIR` (a dotfile, an exported archive, anything an operator dropped in the PVC) can be read and sent to the gateway, while writes are restricted to three extensions (**confirmed**). And `write_file` accepts unbounded `content` while `read_file` truncates at 20000 runes (**confirmed**), so nothing bounds what a runaway generation writes into the workspace.

`read_file`'s truncation notice names the cut and tells the model to use `patch_file` rather than rewrite from the excerpt, but it is prose, not a guard: a `write_file` call carrying a rewritten truncated file still succeeds and drops the tail (**likely**; a length or provenance check on `write_file` against the file it truncated would close it).

`App.handleFileChanged` reloads the editor buffer and resets `lastSavedContent` whenever the changed path is the open file. That path predates this change, but the tool loop makes concurrent editing routine: a teacher typing while Lya patches loses the unsaved buffer (**confirmed** at `App.tsx:237-247`, pre-existing code, newly reachable on every direct-mode edit).

## Tool errors reach the thread disguised as successes

Refusals are normal outcomes by design: a missing or ambiguous `old_string`, a rejected extension, a path outside the workspace all come back as `Erreur : …` in the tool result plus a `StreamEvent{Type:"tool", Tool:{status:"error", error:…}}`. The frontend's `tool` case ignores `status` and `error` entirely — it only checks `status === 'done'` for `jobWroteFiles` — so `isFileOp` sends the event to the thread with the same label as a successful write:

```
✏️ Écriture de B1/unite1.md      <- the write was refused
✏️ Écriture de B1/unite1.md      <- the write succeeded
```

`pi.go` never emits `status:"error"` for a tool, so this event shape is new here and has no rendering path (**confirmed** — `Chat.tsx:372-400`, `tools.ts` `toolLabel`). The teacher's only signal that nothing was written is the absence of the *"Fichier mis à jour par Lya."* note.

`pathFromRawArgs` returns `""` when the arguments are malformed, and `isFileOp` requires a path, so a tool call with unparseable arguments produces no thread entry at all — only a transient `🔧 write_file` line that disappears (**confirmed**).

## Tool-call reassembly, and the branches no test reaches

Turn classification relies on "did any accumulator survive", not on `finish_reason`, which is decoded and never read. A gateway that streams a partial `tool_calls` delta and then finishes with `stop` would have that partial call executed anyway (**likely** — nothing cross-checks `finish_reason`, and the field is dead weight as written).

Not tested: an unknown tool name (`execFileTool`'s default branch), malformed argument JSON, two tool calls in a single turn (`scriptedHermes` supports it, no test uses it, so the `byIndex`/`order` interleaving and sequential execution of multiple calls are unexercised), a gateway that omits `id` (all 13 scripted calls carry one, so the `call_<i>` synthesis never runs), and a `chunk.error` arriving mid-loop after a tool already wrote a file.
