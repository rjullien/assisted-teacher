# Review-fix round on Lya's Desk file tools

The follow-up commit answers the v1 pass on its own terms: the `direct` sub-mode announces `read_file`/`write_file`/`patch_file` in the context line instead of telling Lya she has no workspace access, `deskMode` became three-state so the tools need an explicit `direct` while an absent field keeps only the v1.9.0 write interception, reads got the extension allowlist, writes got a size cap and a refusal to shrink a file served truncated, tool results got a cumulative budget, a write outside the announced working file is flagged, `finish_reason` is cross-checked, failed tool calls have their own frontend label, and the editor buffer is no longer overwritten when it is dirty. Every v1 test gap now has a test, and the suites are green at `34930f9` (backend build/vet/gofmt/test, frontend 9 files / 108 tests, `npm run build`). What did not land cleanly is on the frontend side of the last two fixes, and one of them is a regression rather than a residual.

Watch for: `App.handleFileChanged` now depends on `fileContent`, and that callback feeds `Chat`'s WebSocket effect through `handleStreamEvent`, so every keystroke in the editor closes the chat socket and opens a new one (**confirmed**, blocking); the backend still emits a `running` tool event before each call and the thread renders it with the success label, so a refused write reads as *"✏️ Écriture de …"* immediately followed by the new error line (**confirmed**); once the 60000-char tool budget is spent, a *successful* write is reported to the model as *"Résultat non transmis"*, which invites a retry of a write that already landed (**confirmed**); and a tool call dropped by the `finish_reason` cross-check produces no thread entry, no tool event and a `supported=false` diagnostic (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The backend guardrails are the solid part of this round: each new refusal sits next to the code it protects with a test of its own, the three-state `deskMode` puts the fail-open case where it belongs (a client that never sent the field keeps v1.9.x parity and nothing more), and the single gate is still single, widened by exactly one case in `legacyWritesEnabled`.

The frontend half is where the new problems are. Making the dirty-buffer guard read `fileContent` and `lastSavedContent` from state turned a callback that changed once per file into one that changes once per keystroke, and `Chat` rebuilds its WebSocket whenever that callback's identity changes. The visible consequences are a chat stream that stalls while the teacher types and a Send button that looks enabled while the socket is mid-handshake.

Tool-error rendering is half fixed. The dedicated failure label exists and is tested, but the tests only inject the terminal event; the `running` event the backend emits first still lands in the thread with the completed-write label, so every operation appears twice and a refusal is preceded by a line claiming the write happened.

The context budget solved the overflow it was aimed at and introduced a smaller one next to it. It is applied uniformly to every tool result, so short write confirmations are suppressed alongside long reads once the budget runs out, and it does not cover the assistant message that echoes the model's own `write_file` arguments back — up to 200000 characters per call, unbudgeted, resent on every following turn.

The prompt fix is correct where it applies but rides on the inlining branch: `buildDeskPrompt` only runs when the open file has content, so a freshly created empty file — the natural *"complète ce fichier"* case — goes out with the path-only context line and no mention of the tools.

Two residuals are argued rather than closed, and the arguments hold, but each leaves a hole worth naming: writes are flagged against the announced working file only when a file is open, and keeping a dirty buffer means the chat says *"Fichier mis à jour par Lya."* while the editor shows the old text and the next auto-save overwrites what Lya wrote, with nothing telling the teacher.

<summary>Issues (9)</summary>

1. **Chat WebSocket recycled per keystroke** — `handleFileChanged`'s new `fileContent`/`lastSavedContent` deps propagate into `Chat`'s WebSocket effect via `handleStreamEvent`; read the buffer through refs (or hold `handleStreamEvent` in a ref) so the socket effect stays stable.
2. **`running` tool events render as completed writes** — the thread shows *"✏️ Écriture de X"* for the pre-execution event, duplicating every operation and prefixing every refusal with a false success. Suppress the `running` event in the thread or give it a distinct in-progress label.
3. **Budget suppresses write confirmations** — once `maxToolResultChars` is exhausted, a successful write's short confirmation is replaced by *"Résultat non transmis"*; budget read payloads only, or always let terminal confirmations through.
4. **Echoed write arguments bypass the budget** — the `role:"assistant"` message replays `write_file` arguments verbatim (up to `maxWriteFileChars` = 200000) on every subsequent turn, so the context-overflow path stays open on writes. Budget or truncate the echoed arguments.
5. **Dropped incomplete call is invisible** — the `finish_reason` cross-check discards the call with only a server log: no tool event, a `done` that may carry an empty reply, and `supported=false` in the per-job diagnostic. Emit an error tool event and count the call.
6. **No tool announcement on an empty working file** — the `direct` context line only exists on the `buildDeskPrompt` branch, which requires non-empty `fileContent`. Announce the tools in the path-only branch too.
7. **Working-file flag inert with no file open** — `outsideWorkingFile` returns false when `currentFile` is empty, so in `direct` mode with no file open every write is unflagged while the banner warns nothing is selected. Flag writes when no working file was announced.
8. **Buffer/disk divergence is silent** — when the guard keeps a dirty buffer, the chat claims the file was updated, the editor shows stale content and the next auto-save overwrites Lya's write. Surface it in the thread (`Chat` already handles `file_changed`).
9. **Untested paths in the new frontend behaviour** — no test injects the `running` event the backend emits, nothing covers the `App` wiring of `shouldReloadBuffer` (which is where the regression is), and no backend test asserts what a write confirmation looks like after the budget is exhausted.

## Editor keystrokes now recycle the chat WebSocket

The dirty-buffer guard is right, its wiring is not. `handleFileChanged` reads the buffer from state, so its dependency list grew from `[currentFile]` to `[currentFile, fileContent, lastSavedContent]` (`App.tsx:239-256`), and `fileContent` is updated by Milkdown's `markdownUpdated` listener with no debounce (`Editor.tsx:52-56`, `App.tsx:329`):

```
Milkdown keystroke
  -> setFileContent            (App state)
  -> new handleFileChanged     (App.tsx:256 deps)
  -> new onFileChanged prop    (Chat)
  -> new handleStreamEvent     (Chat.tsx:550 deps)
  -> WS effect re-runs         (Chat.tsx:623 deps)
  -> authWs.close() + new WebSocket
```

`AuthWebSocket.close()` sets `closed` before closing, so `onclose` returns early and no *"Connexion perdue"* is shown — the churn itself is invisible. What is visible: the new socket only resubscribes once it reaches `onOpen`, so typing during a generation stalls the stream and then jumps forward on the replay; and `handleSend` bails on `!wsRef.current?.connected` (`Chat.tsx:631`) while the `connected` state that disables the button stays `true` from the previous socket, so pressing Send right after typing silently does nothing. Each keystroke is also a fresh `/ws/acp` handshake against the backend.

Keeping the buffer and `lastSavedContent` in refs (or holding `handleStreamEvent` in a ref and keeping the effect on `[agent]`) restores a stable socket without giving up the guard.

## The `running` tool event still reads as a completed write

The backend emits two events per call — `running` before execution, then `done` or `error` (`hermes.go:892`, asserted as `read_file:running` + `read_file:done` in `hermes_test.go:899`). `Chat` appends a thread line for any `isFileOp` event regardless of `status` (`Chat.tsx:410-418`), and `toolLabel` has no in-progress branch, so the `running` event of a write is rendered exactly as a finished one:

```
✏️ Écriture de B1/unite1.md          <- running, nothing written yet
⚠️ Échec sur B1/unite1.md : old_string introuvable
```

The new failure label does its job, but the misleading line the v1 issue was about is still on screen, now first instead of alone; successful operations get two identical lines. All four new frontend tests feed only `status: 'done'` or `status: 'error'` (`Chat.test.tsx:523-595`), which is why nothing caught it.

## The budget cuts more than the large reads

`budgetToolResult` (`hermes.go:1003`) is applied to every `role:"tool"` content: read results, error strings and write confirmations alike. Once `maxToolResultChars` is spent, a `write_file` that actually succeeded comes back to the model as *"Résultat non transmis : le budget de contexte des outils est épuisé…"*, so the model cannot distinguish a landed write from a suppressed one and the natural recovery is to write again. The loop also keeps spinning to the cap while every further result is that same notice. Write confirmations are tens of characters — letting terminal confirmations through and budgeting only the read payloads keeps the overflow fix without lying about outcomes.

The overflow path itself is only half closed. Before the results, the loop feeds the assistant turn back verbatim, `arguments` included (`hermes.go:864-879`), and `write_file` arguments carry the whole file content up to `maxWriteFileChars` = 200000 runes — more than three times the entire result budget, unbudgeted, and resent on every following turn. A two-write conversation on a large course file overflows through the echo, not through the reads, and lands on the same *"Échec IA. Réessaie."* the budget was introduced to avoid.

## A dropped tool call disappears completely

The `finish_reason` cross-check (`hermes.go:1224`) discards a call whose arguments do not decode when the turn finished on something other than `tool_calls`. The discard happens in `streamTurn` before the loop counts anything, so `turn.toolCalls` comes back empty, the turn is classified as a plain text answer, `sawToolCalls` stays false and the per-job diagnostic logs `supported=false` — the exact misattribution that line exists to prevent, now reachable from a gateway that does forward `tools`. On the teacher's side there is no tool event at all and, when the cut turn carried no text, the `done` event has an empty `reply`, which `Chat`'s `done` handler drops (`Chat.tsx:451`): the message gets no answer whatsoever. `TestHermesBridge_ToolLoop_IncompleteCallDroppedOnStop` asserts precisely this shape (zero tool events). An `error`-status tool event with the reason, plus counting the call in the diagnostic, would make the drop legible in both places.

## The tool announcement rides on the inlining branch

`buildDeskPrompt` now branches on the sub-mode and the `direct` wording asks for `patch_file` explicitly. But the call site is `agent !== 'pi' && fileContent ? buildDeskPrompt(...) : path-only` (`Chat.tsx:643-648`): with an empty working file the request still declares the three tools while the user turn is the bare `[Contexte: je travaille sur le fichier "X"]`, with no mention that Lya can write it. Creating a file from the tree and asking Lya to fill it is the most direct reading of *"si je dis update ce fichier"*, and it is the one case that gets no announcement.

## What the working-file flag and the buffer guard still leave open

`outsideWorkingFile` returns false as soon as `currentFile` is empty (`hermes.go:984-992`). In `direct` mode with no file open the banner says *"⚠️ Aucun fichier ouvert"* while the tools stay armed, and every write anywhere in the workspace is reported as if it were on the announced file. Flagging unconditionally when no working file was announced costs nothing and matches the flag's stated purpose.

The buffer guard's trade-off — the teacher's unsaved text is the only copy — is the right call, but the divergence it creates is unsignalled: the thread shows *"Fichier mis à jour par Lya."*, the editor keeps showing the previous text, and `useAutoSave` then writes the teacher's version over Lya's. `Chat` is where `file_changed` is handled and it already renders tool lines, so returning the guard's decision and appending a *"tes modifications non enregistrées ont été gardées, le fichier a changé sur le disque"* line would close the loop without new UI infrastructure.

## Test coverage after this round

The v1 gaps are genuinely closed — unknown tool name, malformed arguments, two calls in one turn, an omitted call id, a `chunk.error` after a completed write, and one test per new guard, including an assertion that a refused read's content never reaches the follow-up request and that the anti-shrink refusal leaves the file byte-identical. `runDeskDirectJob` makes "the tools were declared" explicit in every tool test instead of an accident of the default, and `TestFileToolGates` covers the mode × sub-mode × `workDir` matrix.

Not tested: the `running` event in any frontend test, so the duplicated and false-success lines are invisible to the suite; the `App` wiring of `shouldReloadBuffer` (`editorSync.test.ts` covers the pure function only, and the regression lives in the wiring); a write confirmation returned after the budget is exhausted; and the size of the echoed assistant `arguments` across turns.
