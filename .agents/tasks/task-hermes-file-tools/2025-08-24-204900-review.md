# Second fix round on Lya's Desk file tools

The v2 round is answered in commit `66855db`, and the blocking item is closed: `App.handleFileChanged` reads the editor buffer through refs so its dependency list is empty, and `Chat` reads `handleStreamEvent` (and `onSessionChange`, through `patchSession`) through refs so the WebSocket effect depends on `agent` alone. The other eight items are fixed where the dispositions say they are — `running` events go to the transient status line, write confirmations and refusals bypass the result budget under a hard cap, the echoed tool-call arguments are shrunk, a call dropped by the `finish_reason` cross-check produces an error event and counts in the per-job diagnostic, an empty working file gets the tool announcement, a write with no working file announced is flagged, and a kept dirty buffer is reported in the thread. Both suites are green at `f284f66` (backend build/vet/gofmt/test, frontend 10 files / 121 tests, `npm run build`). What remains are edges around the two fixes that changed behaviour rather than guarded it.

Watch for: after a kept dirty buffer the next Desk message inlines the teacher's stale text as the file's content while `read_file` returns the disk version, so a `patch_file` derived from the prompt can miss or land on top of Lya's own write (**confirmed**, mitigated by the new notice); a reload that is attempted but fails returns `true`, so the editor keeps pre-write content with no divergence notice (**confirmed**); and the `supported=true` diagnostic is now also set by calls that were never solicited, in sub-modes where no `tools` array was sent (**confirmed**). All three are follow-up work, not ship blockers.

**Verdict**: APPROVED

## High-level view

The ref-based rewrite holds. `handleFileChanged` no longer closes over `fileContent`/`lastSavedContent`, `patchSession` no longer closes over `onSessionChange`, and the socket effect's dependency list is `[agent]` — the only value that selects the endpoint. `Chat` was fixed too, not just `App`, so any parent handing it an unstable callback can no longer recycle the socket. Writing the refs during render is outside React's contract, but with these values the window is not reachable.

The dirty-buffer guard is now reported to the teacher, which closes the "the AI said it wrote the file and nothing changed" loop. Two edges remain around it: the stale buffer keeps being inlined into the next Desk request, so the prompt and the disk disagree while Lya is being asked to patch that file; and a reload whose fetch fails is indistinguishable from one that succeeded, so the editor silently keeps pre-write content.

Routing `running` events to the transient status line fixes the duplicated and false-success lines for both bridges from one predicate in `tools.ts`. Mode Pi inherits it, and is slightly worse off in one case: an operation whose terminal event never arrives now leaves no trace in the thread, where it used to leave the announcement line.

The context-overflow work is coherent now — only `read_file` payloads are cut, and the assistant echo no longer replays a whole rewritten course file on every turn. Two soft spots are left in the accounting: exempted messages are counted but not bounded by the remaining budget, and `shrinkEchoedArgs` only shrinks top-level string fields without re-checking the marshalled size, so anything outside the declared argument schema is echoed unbounded.

Making a dropped call visible was right, but it was wired unconditionally: `droppedCalls` feeds `sawToolCalls` before the `toolsEnabled` check, and `streamTurn` emits the error event whatever the sub-mode. A job that never declared `tools` can therefore log `supported=true` and show a tool failure in the copie/insertion thread, which dulls the one greppable line that exists to settle whether the real gateway forwards `tools`.

The constraints hold: `pi.go`, `LyaChat.tsx` and `version.json` are byte-identical to `main`, `buildDeskPrompt` and `MAX_INLINED_FILE_CHARS` are intact with the inlining active in both sub-modes, `fileToolsEnabled` still requires `mode=desk` + `direct` + a workspace, unsolicited calls are refused, a turn with no `tool_calls` still costs exactly one request, the diagnostic line is emitted once per job, and nothing is tagged, pushed or bumped.

1. **Stale buffer feeds the next prompt** — after the guard keeps a dirty buffer, `buildDeskPrompt` still inlines that buffer as the file's content while `read_file` returns the disk version; a `patch_file` whose `old_string` came from the prompt can fail or overwrite Lya's write. Inline nothing (or the disk version) while a known divergence stands.
2. **Silent failure of an attempted reload** — `handleFileChanged` returns `true` whenever `shouldReloadBuffer` said yes, even if the `getText` failed, so the teacher gets no notice and a stale editor. Return `false` when the fetch did not land.
3. **Divergence notice repeats per write** — two writes to the same dirty working file in one job append two identical `chat.bufferKept` paragraphs, which reads like two incidents. Deduplicate per file, per job.
4. **Mode Pi loses the trace of an unfinished tool** — with `running` events moved to the transient status line, a pi tool whose `tool_execution_end` never arrives leaves nothing in the thread. Keep a terminal line when the job ends with a tool still running.
5. **`supported=true` for unsolicited calls** — `droppedCalls` sets `sawToolCalls` before the `toolsEnabled` check, so a job that declared no `tools` can log `supported=true`; the same holds for well-formed unsolicited calls. Gate the diagnostic on `toolsEnabled`, or use a distinct token.
6. **Dropped-call error shown where no tool was announced** — `streamTurn` emits the `error` tool event regardless of sub-mode, so a copie/insertion thread can show "Échec de l'outil …" for a tool the teacher was told does not exist. Emit it only when the tools were declared.
7. **`maxEchoedArgsChars` is not actually enforced** — `shrinkEchoedArgs` shrinks top-level string fields only and returns the marshalled result without re-checking its size, so extra keys or a long array/object argument are echoed unbounded. Re-truncate after marshalling.
8. **Exempted messages overshoot the result budget** — `alwaysDeliver` skips the `remaining` check, so confirmations and refusals can push the cumulative total past `maxToolResultChars` by up to `maxConfirmationChars` per call. Bounded and small in practice; cap the overshoot if the budget is meant to be hard.

## The keystroke-per-socket chain is broken in two places

The chain the v2 pass traced was `setFileContent` → new `handleFileChanged` → new `onFileChanged` prop → new `handleStreamEvent` → WS effect re-run → `close()` + new `WebSocket`. It is cut at the first link (`App.tsx:255-282`: the callback reads `currentFileRef`/`fileContentRef`/`lastSavedContentRef` and has deps `[]`) and again at the fourth (`Chat.tsx:552-556`, `handleStreamEventRef`, effect on `[agent]`). `onSessionChange` got the same treatment (`Chat.tsx:317-333`), which matters because `App` hands `Chat` a different setter per agent.

The refs are assigned in the render body, not in an effect. React does not guarantee that a render commits, so a discarded render can in principle leave a ref ahead of committed state; here the values are the editor buffer and callbacks read only from socket callbacks after commit, so the window is not reachable in practice.

## Divergence after a kept dirty buffer

The guard is right and the notice closes the visible half of the problem, but the invisible half moved into the prompt. `Chat.handleSend` inlines the `fileContent` prop — the editor buffer — into every Desk request (`Chat.tsx:713-720`), and after a kept divergence that buffer is the teacher's stale text while the disk holds Lya's write. The next message therefore tells Lya "voici le contenu du fichier" with content the file no longer has, while `read_file` in the same conversation returns the real one:

```
disk        : Lya's version   (written, file_changed emitted)
editor      : teacher's text  (kept, dirty)
next prompt : teacher's text  (inlined as the file's content)
read_file   : Lya's version
```

A `patch_file` whose `old_string` was copied from the inlined text then either fails with "old_string introuvable" — recoverable, the model is told to re-read — or, when the fragment survives in both versions, applies on top of a write the teacher cannot see. The `chat.bufferKept` wording does tell the teacher to save or reopen before continuing, so this is follow-up work rather than a hole, but the prompt is the one place the divergence is not acknowledged (**confirmed**).

Two smaller edges sit next to it. `handleFileChanged` computes its return value from `shouldReloadBuffer` alone, so a reload that was attempted and whose `getText` failed still returns `true` (`App.tsx:283`): buffer and disk diverge, `lastSavedContent` still matches the buffer, and nothing is said (**confirmed**). And nothing deduplicates the notice: a job that writes the working file twice while the buffer is dirty appends the same paragraph twice (**confirmed**).

## What mode Pi gives up with the `running` events

The thread line for a file op now comes only from the terminal event (`Chat.tsx:437-459`), and `pi.go` — correctly left untouched — emits `tool_execution_start` → `tool_execution_end` pairs. When pi dies or is cut mid-tool the `end` event never arrives and the operation leaves nothing behind, where the announcement line used to be the only record that the agent had started touching a file (**likely**; it depends on pi's exit path, and the same gap means no `file_changed` is emitted either, so the editor stays consistent with the thread).

## Budget, echo, and what stays unbounded

`budgetToolResult(result, used, alwaysDeliver)` with `alwaysDeliver = tc.name != "read_file"` puts the cut where a cut cannot lie. The exemption is counted against the budget but not bounded by it — `alwaysDeliver` returns before the `remaining` check — so the cumulative total can exceed `maxToolResultChars` by up to `maxConfirmationChars` per exempted call. With eight loops and a couple of calls per turn that is a bounded overshoot on messages that are a few dozen characters in practice, but the constant no longer means what its name says (**confirmed**).

`shrinkEchoedArgs` closes the larger hole: a `write_file` no longer replays up to 200000 characters of file content on every following turn. Its bound is enforced only for the shapes the declared schema can produce — only top-level string fields are truncated, non-string values are left alone, and the re-marshalled JSON is returned without re-checking its length (`hermes.go:1040-1071`), so a model that adds keys or passes a long array is echoed above the cap. `TestShrinkEchoedArgs` asserts the bound for one long string and for undecodable input, which is why this is not caught (**confirmed**, low impact: the tool schema only declares strings).

## The diagnostic now counts calls nobody asked for

Making the dropped call visible was the right response — a `done` with an empty reply and a server-side log was the worst possible outcome for the teacher. But both halves of the fix ignore whether tools were declared. `droppedCalls` feeds `sawToolCalls`/`toolCallCount` at `hermes.go:863-869`, before the `!toolsEnabled` refusal at `hermes.go:879-886`, and `streamTurn` appends the `error` tool event unconditionally (`hermes.go:1328-1340`). So in the copie/insertion sub-mode, or in mode Lya, a model that emits a malformed `tool_calls` fragment when no `tools` array was sent produces `hermes: tool_calls supported=true (mode=desk deskMode=insert …)` and a `⚠️ Échec de l'outil …` line in a thread whose banner promises no file access. `deskMode` is in the log line so a human can still disambiguate, and the same conflation already applies to well-formed unsolicited calls, but this is the single line the task relies on to settle the one thing that cannot be tested from here — whether the real gateway forwards `tools` (**confirmed**).

## Test coverage after this round

Both v2 blind spots are covered by tests that fail on the old code, and the frontend ones test behaviour rather than the fix's own helpers: `App.test.tsx` collects every distinct `onFileChanged` identity `Chat` received in a `Set` and asserts its size is still 1 after four keystrokes, and `Chat.test.tsx` counts constructed WebSockets across re-renders that change both `fileContent` and the callback identity, then pushes a `file_changed` frame through the surviving socket and asserts the *fresh* callback receives it and the stale one does not — so a ref captured once fails as loudly as a recycled socket. On the backend, `TestHermesBridge_ToolLoop_BudgetKeepsWriteConfirmations`, `…_EchoedWriteArgumentsAreShrunk` (with an assertion that the file on disk still got the full content) and `…_DroppedCallStillCountsAsSupported` (capturing the diagnostic log line, the only place that behaviour is observable) cover the rest.

Not tested: the divergence path end to end (a write on a dirty buffer followed by the next prompt, i.e. the stale inlining above); a reload whose `getText` fails; a second `file_changed` on the same dirty file; a pi tool that never sends its terminal event; the diagnostic for a dropped call in a sub-mode where no tools were declared; and `shrinkEchoedArgs` with a non-string or extra argument.
